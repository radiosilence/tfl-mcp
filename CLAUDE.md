# tfl-mcp

An MCP and GraphQL server over the Transport for London Unified API, built as the `tfl` binary. `crates/tfl-api-client` is generated from TfL's OpenAPI spec by `cargo xtask regen` and never edited by hand; `crates/tfl-mcp` is the server. It ships as a container image (`ghcr.io/radiosilence/tfl-mcp`), which jaritanet deploys behind mcp-gateway by tracking this repository's releases, and as signed binaries on each GitHub release.

## Git

- Work in PRs; never push to main. PRs are squashed; merge main into a branch rather than rebasing.
- Never push tags. CI tags and publishes when a release PR merges.
- Commits are signed.

## Changelog

`CHANGELOG.md` is generated by `scripts/changelog.py` and never edited by hand. Every change adds one fragment under `changelog.d/unreleased/<section>/`, named `<pr>-<slug>.md` and holding one `- **Lead.** Detail.` entry; to correct a note, edit its fragment. `just changelog --stdout` previews the result. The format is in `changelog.d/README.md`.

## Releasing

`just release patch|minor|major` (or an exact `X.Y.Z`) branches from main, bumps `crates/tfl-mcp/Cargo.toml` and `Cargo.lock`, turns the unreleased fragments into the version and opens the release PR. Merging it is the release: CD tags the image already built for that commit `vX.Y.Z`, `vX.Y`, `vX` and `latest`, then creates the GitHub release with the binaries and the changelog section as notes. The image goes first because jaritanet pins `vX.Y.Z` as soon as the release exists. A push releases only when it changes the version and that version is not yet released; `gh workflow run ci-cd.yml` on main retries a release that failed part way.

## CI/CD

`.github/workflows/ci-cd.yml` is one pipeline. CI ends in `Checks`, the only status a ruleset should require; CD runs after it on main, in the same run, and ships what CI built.

Most jobs run only when the change touches their domain, so a skipped job is expected and passes `Checks`; a failed or cancelled one fails it. The `changes` job decides from the diff (against the base on a pull request, against the last main commit whose run passed on a push), and a manual run, a release PR or a diff it cannot compute runs everything. Markdown never counts, and anything under `.github/` counts for every domain.

- `rust`: crates, xtask, the manifests, `Cargo.lock`, `.cargo/`. Runs `Format` and `Linux` (clippy and the tests).
- `codegen`: the generated client, xtask, `codegen/`, and a `Cargo.lock` change that reaches xtask's dependencies. Runs the drift check.
- `apple`: what the Linux jobs cannot vouch for on macOS: manifests, build scripts, `.cargo/`, the toolchain, a `Cargo.lock` change that reaches tfl-mcp's dependencies, or code near a `cfg` for an Apple target. Runs `macOS` (the tests). The account's macOS runners are few and shared, so a plain source change does not take one.
- `docker`: `Dockerfile`, and on main any `rust` change, since CD ships the binaries. Runs the musl builds and the image.

`Changelog` always runs. Whether a `Cargo.lock` change reaches a domain is decided by `.github/scripts/lock_inputs.py`; if it fails, the change counts. To add a domain, add its output to `changes` with an allowlist of paths, gate its jobs with a job-level `if:`, and add them to `needs:` of `checks`.

Main pushes the image as `:<sha>` while the checks run; CD moves `main` and `sha-<short>` onto it once they pass, and a release adds the version tags. The release binaries are built once: the Linux tarballs are what the image holds and what the release attaches, and the macOS release build starts alongside the checks.
